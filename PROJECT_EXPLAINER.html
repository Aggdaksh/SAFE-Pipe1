SAFE-Pipe, from the beginning

We run the same kind of data pipeline with different resource settings, learn how long each setting takes, and recommend a setting that should finish before a deadline at low resource cost.

This page starts with ETL concepts and ends with the actual code, measurements, Git branch, and remaining work. It is a teaching guide; the linked reports and files hold the reproducible evidence.

1. What problem are we solving?

Imagine a nightly pipeline that reads Parquet files, filters rows, groups or joins data, and computes a result. It has a deadline: perhaps it must finish before the morning report. You can give its processing engine more workers, more threads, or more memory. Those choices change both runtime and resource usage.

Too little capacity

The job may run slowly, miss its deadline, or fail under memory pressure.

Too much capacity

The job may finish, but reserve more CPU and memory than necessary.

SAFE-Pipe's question: Before this job starts, which of our eight allowed Dask settings has the lowest estimated resource cost while its cautious runtime estimate meets the deadline? If the job is unlike our measured workloads, or no setting qualifies, the system can abstain and ask for a human decision.

Scope: This is a university Project-I prototype using synthetic data and one local PC. Its “cost” is a normalized measure of local resource use, not an AWS bill. It has not measured AWS Glue or a multi-machine cluster. Read the B-lite synopsis.

2. The minimum data engineering background

Pipeline / ETL

A sequence of steps that reads data, transforms it, and produces a result. Here the transformations are four deliberately chosen patterns, not a business production pipeline.

Parquet

A file format for tabular data. The project generates versioned Parquet inputs so runs can be compared on the same bytes.

Dask

A Python framework that breaks data work into tasks. Here it runs on a LocalCluster on one PC; workers have explicit memory limits.

Configuration

The resources assigned to Dask: 1 or 2 workers × 1 or 2 threads per worker × 1 or 2 GB per worker. That gives 8 combinations.

A workload family means the operation pattern. The project measures scan/filter, group-by, skewed join, and a key-based sort/shuffle workload named sort_merge. Those patterns stress resources differently.

Parquet input→Dask tasks→Measured run→Runtime model→Recommendation

The deadline is called an SLA in this project. A run is one workload family executed once with one setting. A repeat reruns that same pair because timings vary.

Four tiny examples of what the code computes

The following rows are made-up teaching data, small enough to calculate by hand. The physical experiment uses much larger generated Parquet files. The links point to the real Dask operations.

Teaching rows

Scan/filter: keep matching numbers, then average

Suppose the value column is 0.2, 0.8, 0.6. The code keeps values greater than 0.5, giving 0.8, 0.6. Their mean is 0.7. The real expression is frame.loc[frame["value"] > 0.5, "value"].mean(). A separate flag column exists in the generated input, but this measured operation does not use it.

Teaching rows

Group-by: add per key, then average the group totals

Group A totals 2 + 3 = 5; group B totals 5. The code then averages those two totals: (5 + 5) / 2 = 5. It times the computation rather than saving an output table.

Teaching rows

Skewed join: match keys between two tables

Left table: (K1, payload 4), (K1, payload 2), (K2, payload 7). Right table: (K1, dimension X). An inner join keeps the two K1 rows, and the code sums their left-side payload: 4 + 2 = 6. If many rows share K1, that key is skewed and can create uneven work. The real generator deliberately produces such uneven keys.

Conceptual operation

sort_merge: shuffle by key

Imagine rows arriving with keys 3, 1, 2. set_index("key", shuffle="tasks") redistributes them into key-ordered Dask partitions. The code then takes the first payload from each resulting partition and sums those values, forcing the shuffle to run. The exact scalar depends on partition boundaries. Despite its name, this current benchmark does not join or merge a second table.

3. What has the team built?

  1. Describe the job before running it.

    A workload profile includes its family, input size, estimated rows, file and partition counts, and a skew indicator. It does not include the job's actual result or runtime. See feature list and schemas.

  2. List the allowed settings.

    The frozen grid has eight candidates. For example, w1_t2_1g means one worker, two threads, and a 1 GB memory limit for that worker.

  3. Estimate runtime, with a cushion.

    A fitted LightGBM model predicts a typical successful runtime. A one-sided conformal calibration adds an upper bound used for the SLA check. The bound is a cautious estimate, not a promise.

  4. Reject unsupported or unsafe choices.

    The out-of-distribution (OOD) gate marks an unfamiliar family or large size shift; a simple memory rule can reject a candidate. The failure field is a rule flag because no measured job failed.

  5. Choose or abstain.

    The optimizer keeps candidates whose upper runtime is within the SLA and whose guards pass. Among those, it chooses the smallest expected normalized cost. If none qualify, it abstains.

Decode a setting

What does w2_t2_1g buy?

w2 means two worker processes; t2 means two threads in each, so the project counts 2 × 2 = 4 allocated vCPUs. 1g means a 1 GB limit for each worker, so the counted memory is 2 × 1 = 2 GB. If its predicted runtime were 3 seconds, its illustrative cost would be 3 × (4 + 2) = 18 normalized units. The PC itself has more RAM, but that does not change these worker limits. See grid.py and cost.py.

At a high level, generate.py makes repeatable Parquet inputs, execute_dask.py defines the Dask calculations, collector.py times one run, runtime.py predicts duration, and optimizer.py makes the final choice. The CLI ties these parts together.

A key rule: A prediction may use only information available before a run. Feeding the actual runtime or status into its own prediction would be data leakage and make the evaluation misleading.

6. How does one recommendation work?

Suppose a sort job arrives with a 13.1 second SLA. The command recommend-model creates one pre-run feature row per allowed setting, predicts each runtime and upper bound, calculates cost, checks the guards, and returns one setting or abstention.

Real frozen sort example: It chose w1_t2_1g. Its point runtime estimate was 3.30 s, and its upper estimate was 5.57 s, below the 13.1 s SLA. The three measured runtimes for this family/setting were 5.083, 5.566, and 5.342 s. This is an illustration from the measured table, not an independent validation case. Demo evidence.

The formula is expected normalized cost = predicted seconds × (allocated vCPUs + allocated GB). For w1_t2_1g, that is approximately 3.30 × (2 + 1) = 9.90 local cost units. The point estimate sets cost; the more cautious upper estimate tests the deadline. The formula is a comparison tool, not money.

Actual table comparison

Prediction, deadline, and measurement are different numbers

The policy's 3.30 s point estimate produced the 9.90 expected-cost score. Its 5.57 s upper estimate passed the 13.1 s deadline. After execution, the three actual runtimes had a 5.342 s median, giving 16.026 median measured cost units. For the declared default w1_t1_2g, the sort-family median was 6.946 s and 20.839 units. Both choices met this family's SLA; these same-table measurements are an illustration, not a new independent experiment. Sources: CSV and policy report.

Teaching scenario

When does the system refuse to choose?

If the smallest upper estimate among all settings were 7 s but your deadline were 5 s, no candidate passes, even if a point estimate is faster than 5 s. The optimizer abstains. The OOD gate also marks a workload red if it is too far from its measured size: a roughly 178 MB sort input is the measured profile; 240 MB is roughly 35% larger and would be yellow, while 540 MB is more than twice as large and would be red. Yellow does not automatically reject a setting; red does. These size thresholds are hand-set heuristics, not validated failure probabilities. See ood.py.

7. What do the results prove?

96/96jobs succeeded and met SLA
13.84%test median absolute percentage runtime error
24/24held-out rows within the runtime upper bound

The model was tested on 24 rows from eight held-out family/setting pairs. All three repeats of a pair stayed in the same training, calibration, or test group. LightGBM's runtime MdAPE was 13.84%, versus 23.01% for a simple family-median baseline. The upper bound covered all 24 test rows; that does not mean it will cover every future job. See runtime model report.

Why the split matters

Keep related repeats together

Suppose three timings for the same family and setting are 5.1, 5.3, 5.2 s. Putting two in training and the third in test would let the model see almost the same situation beforehand. SAFE-Pipe keeps all three in one group. The real split used 36 training rows / 12 pairs, 36 calibration rows / 12 pairs, and 24 test rows / 8 pairs. Those sets serve different purposes: fit the model, size its upper cushion, and evaluate unseen pairs. See the frozen split.

For intuition, if a model predicts 5 s and the job takes 6 s, its absolute percentage error on that row is |6 − 5| / 6 ≈ 16.7%. MdAPE is the median of such errors across test rows. The real conformal cushion is calculated from grouped log-runtime errors; its fitted multiplier is about 1.688, which is why a 3.30 s point prediction becomes about 5.57 s upper. This simple example does not replace the actual calibration calculation.

In a same-table comparison, the selected settings had mean median normalized cost 7.524 versus 11.421 for the declared default, about 34.1% lower in that table. Some settings in the evaluation table were also used to train the model, so this is descriptive and cannot establish a general cost improvement. See policy report.

Important limits: All 96 jobs succeeded, so there are no observed failure examples to train or validate a failure predictor and no measured safety advantage. Worker peak memory was not captured reliably. The OOD thresholds are cautious hand-set rules based on only one measured size per family. Dask memory warnings on some successful 1 GB sorts do not prove spill or failure.

10. Terms you can return to

SLA (service level agreement)

Here, a per-family finish-time deadline in seconds. A candidate qualifies only when its predicted upper runtime is at or below that deadline.

Worker, thread, and memory limit

A worker is a Dask process. Threads let a worker handle more work concurrently. The 1 GB or 2 GB memory limit is per worker, not the PC's total RAM.

Skew

An uneven distribution of keys. A few very common keys may make a join or grouping more demanding than a balanced dataset of similar size.

JSONL, CSV, and manifest

JSONL stores one JSON result per line for append-only collection. CSV is the compact shareable table. A manifest describes a generated dataset and its fingerprints so we can check that later runs use the intended files.

Model training, calibration, and test

Training fits the runtime model. Calibration learns how much cushion to add. Test holds out family/setting pairs to estimate performance on pairs the fit did not see.

LightGBM and conformal bound

LightGBM is the tabular model used to predict successful runtime. Split conformal calibration uses held-out errors to create an upper estimate. The measured 24/24 test coverage is small-sample evidence, not a guarantee.

OOD and abstain

Out-of-distribution means a workload differs from the measured scope, such as a new family or a large input-size shift. To abstain means return no recommended setting instead of making a weakly supported choice.

MdAPE and normalized cost

MdAPE is median absolute percentage error: the typical relative gap between predicted and actual runtime in the test set. Normalized cost here is runtime multiplied by the sum of allocated CPU and GB units; it is not a cloud price.

Branch and pull request

A Git branch is a line of changes. The Windows work is on codex/windows-dask. A pull request lets teammates review those changes before merging them into main.

Check your understanding

Why are there 96 rows if there are only four workload families?

Each family ran under eight settings, and each family/setting pair ran three times: 4 × 8 × 3 = 96.

If the point runtime is 3.3 s, why check 5.57 s against the SLA?

The point estimate drives expected cost. The calibrated upper estimate adds a cushion for uncertainty and is the number used to decide whether the deadline is likely to be met.

Does 96 successful jobs prove that the system reduces failures?

No. With zero observed failures, there is no measured failure difference between policies and no positive failure examples for a learned failure model.
