01 · First, the whole project

SAFE-Pipe helps choose how a data job should run.

The same data operation can run with different numbers of workers, threads and memory limits. Those choices affect time, allocated resources and sometimes whether the operation completes.

Imagine a university office has a large spreadsheet of purchases. It wants to group the rows by department and calculate each department’s total. It could assign one person to the work or split it among several people. More people might help, but coordination also takes time. The equivalent computer choices are our configuration settings.

Describe the workOperation, input size and other known details
→
Compare settingsEstimate runtime and check constraints
→
Return a decisionRecommend one setting, or abstain

The submitted project title is “SAFE-Pipe: Failure-Aware Cost and Runtime Optimization of Distributed Data Pipelines under SLA Constraints.” The measured implementation is more specific: memory-capped local Dask on one Windows PC. It is not a measured AWS Glue service or a multi-machine cluster.

Original advisor · on main

Track 1: predict before execution

Train a LightGBM model from a small measured table. For a known workload, estimate the runtime of eight settings and recommend an eligible setting.

Key evidence: 96 physical jobs, 13.84% test MdAPE, explained recommendation interface.

Later research · separate branch

Track 2: ask whether a small trial helps

Run controlled development studies to see whether a small sample predicts full-job behaviour and improves decisions after paying its own cost.

Key evidence: a 768-attempt screen, 48 Stage A full runs, 96 Stage B probes, and a negative one-probe feasibility result.

The most useful distinction in this entire guideThe newer probing research did not retrain the original LightGBM model. It investigated a different decision strategy. Its runtime comparisons, memory observations and software tests are different kinds of evidence.

02 · Vocabulary, starting from zero

A job, a task and a worker are different things.

TermSimple meaningExample in our project
Data pipeline / ETLA sequence that reads data, transforms it and produces an output. ETL means extract, transform, load.Read Parquet files → filter or group rows → compute a result.
Workload / jobThe complete piece of computation we want finished.“Calculate grouped sums on this dataset.” One benchmark attempt executes one workload under one setting.
TaskA smaller scheduled unit inside that computation.Read one partition, calculate a partial sum, or merge intermediate results.
PartitionOne chunk of a larger dataset.An input is split across eight or sixteen files/partitions, depending on the study.
DAGDirected acyclic graph: tasks linked by dependencies, without a loop.A merge must wait until the required partial results exist.
SchedulerThe coordinator that decides which worker gets each task.Dask assigns ready tasks and tracks their results.
WorkerA process that carries out tasks and holds data.Our research usually uses two worker processes on this one PC.
ThreadAn execution lane within a worker process.Two workers × one thread each gives two configured execution lanes.
Run / attemptOne recorded execution, including its outcome.Run repeat 2 of a groupby job at a 1 GB-per-worker setting.
CellOne identity in an experimental matrix.A particular workload + method + configuration + repeat. A failed cell is still a recorded attempt.

Why did we use these operations?

Scanning tests reading and filtering. Groupby combines rows with the same key. A join matches rows from two tables. Sorting rearranges rows by a key. They are recognisable data-engineering patterns with different resource demands. We did not select an isolated “task” as the whole project; we studied configuration selection for jobs made of many tasks.

A tiny groupby

Input: IT ₹100, HR ₹50, IT ₹200.
Output: IT ₹300, HR ₹50.

The real benchmark uses synthetic numeric records. This purchase example only explains the operation.

A tiny join

Orders contain customer IDs. A customer table contains an ID and region. Joining adds each customer’s region to their orders.

A shuffle may move rows so matching keys reach the right worker. That coordination can require memory and network/IPC work.

A two-worker, 1 GB-per-worker cluster has about 2 GB of configured worker memory. The host has approximately 31.4 GiB of physical RAM, but the experiment deliberately applies smaller worker limits. The scheduler, parent process, operating system and other apps also use RAM.

More workers does not automatically mean a faster job.There is a cost to starting processes, splitting work, shuffling data and joining results. For small jobs, extra coordination can outweigh extra parallelism. That is why we measured settings instead of assuming the largest one would win.

GB and GiB are different units: 1 GB = 1,000,000,000 bytes; 1 GiB = 1,073,741,824 bytes. The original fitted feature contract had legacy memory parsing. The later advisor scores use explicit SI/IEC byte parsing; we preserve the old fitted features rather than silently changing their meaning.

06 · Before a new prediction

LightGBM sees a small description, not the entire dataset.

The original model predicts successful engine runtime in seconds. It receives one feature row for each workload/configuration combination. To compare eight settings, we form eight feature rows: the workload description stays the same; the configuration fields change.

Six workload descriptors

family, input_bytes, estimated_rows, file_count, partition_count, skew_score.

They describe what kind of operation it is, its input size and layout, and the declared skew tag.

Six setting descriptors

config_id, n_workers, threads_per_worker, memory_limit_gb, allocated_vcpus, allocated_gb.

They describe the candidate we are asking the model to evaluate.

These are 12 named input fields. Family and configuration ID are converted into indicator columns (“is this groupby?”, “is this setting w2…?”). The saved fitted feature list contains 22 encoded columns.

Workload description + candidate setting → predicted log(runtime) exp(predicted log(runtime)) → point runtime in seconds

The target label during training is the measured engine_seconds, transformed with a natural logarithm. The model does not get a job’s future runtime, future spill, failure status or future peak RAM as its own prediction input. That would give away the answer, which is called data leakage.

Show a real original feature-row example

From the frozen main-v1 groupby profile with setting w1_t1_1g:

family = groupby input_bytes = 198,487,831 estimated_rows = 14,970,000 file_count = 16; partition_count = 16; skew_score = 0.1 config_id = w1_t1_1g n_workers = 1; threads_per_worker = 1 memory_limit_gb = 1.0 allocated_vcpus = 1.0; allocated_gb = 1.0

The 0.1 skew score is a frozen descriptor from this original workload contract, not a newly learned probability. Selecting another candidate changes its setting fields. Inference loads the saved model; it does not train a new one before each job.

Three things that sound like “parameters”Input features describe a particular request. Training hyperparameters control how LightGBM learns. Decision preferences express how we trade speed against configured resources. They belong to different layers.

07 · Training, explained simply

LightGBM learns a series of small corrections.

LightGBM is a gradient-boosted decision-tree library. A decision tree asks a sequence of questions about input values and ends in a numerical estimate. Boosting builds multiple trees so later trees help correct earlier mistakes. In our case the numerical target is log runtime.

Start with training rowsKnown workload + setting → measured runtime
→
Fit small treesLearn patterns and correct residual errors
→
Save the modelReuse the learned tree ensemble for inference

A toy tree might ask, “Is the operation a sort?” and “Does this setting have more than one execution thread?” Those questions are illustrative; they are not a transcription of our fitted trees. The actual model contains learned split thresholds and leaf values.

Training settingValuePlain-English meaning
n_estimators120The configured number of boosting trees/rounds.
num_leaves7Maximum leaves per tree, keeping each tree small.
learning_rate0.05Scale down the contribution of each new tree.
min_child_samples3A minimum-data constraint on leaves.
reg_lambda1.0L2 regularization: discourages overly large fitted leaf values.
random_state2026Recorded random seed for reproducibility.
n_jobs1One training thread. This is separate from Dask worker threads.

We fitted this original model once on the frozen training split. These hyperparameters were fixed, not presented as the result of an extensive hyperparameter search. The later advisor and probe work did not create a new trained model.

Why use the log of runtime?

Runtime is positive and its differences often make sense as ratios: 2 seconds versus 4 seconds is a doubling, as is 10 versus 20 seconds. Learning on a log scale represents those multiplicative differences. We exponentiate the model output to get seconds again. The calibration upper bound also uses a multiplicative factor.

Do we have a deep-learning model?The core fitted predictor is LightGBM, a boosted-tree model. Optional TabPFN work was proposed but is not recorded as executed. Do not describe a proposed comparison as an implemented model.

08 · How we separated the data

Training, calibration and testing have different jobs.

The table contains 32 family/configuration groups, each with three physical repeats. A group is, for example, “groupby at w2_t1_2g.” We kept all three repeats of a group together.

  1. Training: the model learns its tree structure and values from 36 rows.
  2. Calibration: 36 different rows are used to set the cautious upper-runtime adjustment, without refitting the trees.
  3. Test: 24 remaining rows assess point errors and observed upper coverage.

Why not randomly split all 96 rows?

Suppose repeat 1 of one setting enters training and repeat 2 of that identical workload/setting enters testing. The test is then very similar to something the model has already seen. Keeping repeats together avoids that particular leakage.

The important limit remainsAll four workload profiles are represented in this study. Holding out some settings is not the same as testing completely unseen workload families, new sizes, new skew patterns or new hardware. The effective test diversity is eight family/configuration groups, not 24 independent new workload types.

The original predictor only learns from successful jobs. All 96 original scored jobs succeeded, so this table cannot teach a failure classifier what failure looks like.

Sources: frozen split · grouping rationale.

09 · Read the results correctly

Our headline model metric is error, not classification accuracy.

A classifier predicts a category such as “spam / not spam.” Our runtime regressor predicts a number such as “3.2 seconds.” A prediction can be slightly wrong or very wrong, so a percentage-error metric is more informative than a simple right/wrong accuracy.

Absolute percentage error = |predicted − actual| ÷ actual × 100 MdAPE = median of the individual absolute percentage errors

Example: actual runtime 10 seconds, predicted runtime 12 seconds → 20% error. For errors 5%, 10% and 40%, the median is 10%. The median is the middle value after sorting; for an even count, it is the average of the two middle values.

10 · Why give two runtime numbers?

A point estimate is our guess. An upper estimate adds caution.

If the model predicts 3 seconds and the deadline is 3.1 seconds, accepting on the point estimate alone leaves little room for underprediction. We therefore compare an upper runtime estimate with the deadline.

The original calibration uses one-sided split conformal logic. In plain language: look at how much the model underestimated calibration jobs, group each setting’s three repeats, and use a conservative ranked residual to set an adjustment. The saved log adjustment is 0.523642.

Upper estimate = point prediction × exp(0.523642…) ≈ point prediction × 1.688

For an illustrative 3.00-second point prediction, the upper estimate is approximately 5.06 seconds. With a 5-second deadline that candidate would be rejected; with a 6-second deadline it could pass this particular check.

90%Nominal calibration target used by the method, with alpha = 0.1.
24 / 24Observed held-out row coverage; all eight test groups were also covered. Mean upper-minus-point width: 1.33 seconds.
Coverage is not the same as success probability.Observed 24/24 coverage in a small test does not prove universal 100% coverage, nor does it prove 90% success for a setting selected by the policy or for new workload profiles. Those are different claims that need separate evidence.

An SLA is a deadline or service requirement. In the original advisor, the deadline concerns engine execution; cluster startup, profiling and advice time are outside that frozen target. Later research pays attention to full lifecycle and complete-request costs because users experience those too.

Sources: calibration details · deadline contract.

11 · Turn predictions into a recommendation

Predict, reject unsuitable candidates, then compare the survivors.

  1. Check support: the explained advisor requires an exact match to a frozen workload description and matching fitted artifacts.
  2. Predict all eight candidates: get a point runtime and upper estimate for each.
  3. Apply constraints: deadline, optional thread/memory budgets and a coarse input-memory rule.
  4. Rank eligible settings: use the declared objective.
  5. Return a recommendation or abstain: explain eligibility and rejection reasons. Inference does not automatically execute the selected job.

The original and newer objective are different formulas

The historical recommend-model policy uses point runtime × (allocated vCPUs + allocated GB). The newer advise layer normalizes configured resources and supports balanced, resource and fastest modes. They share the same fitted predictor, but their scores and selected settings can differ.

P = workers × threads per worker M = total configured memory in bytes Q = 0.5 × P/4 + 0.5 × M/4,000,000,000 R = (predicted time / deadline) × Q J = beta × (predicted time / deadline) + (1 − beta) × R beta = 0.5 balanced; 0 resource; 1 fastest Choose the eligible candidate with the smallest J.

These weights express preferences; they are not learned LightGBM parameters. The score is dimensionless and uses configured resources. It is not a bill in rupees/dollars, measured electricity consumption or actual RAM utilization.

12 · What midterm did not settle

A working prototype is not the same as independent validation.

  • Only four original profiles: new sizes, partitioning, skew or hardware were not established as supported.
  • No learned failure model: zero original failures meant no usable positive examples for one. The old p_fail output was a deterministic 0/1 guard flag, not a calibrated probability; the newer advisor exposes failure probability as null.
  • Weak original memory measurements: reliable per-worker peak/spill data were not captured in the 96-row study. Later research telemetry does not retroactively fix those original rows.
  • Descriptive policy comparison: it reused the model’s source table. Fresh predeclared policy decisions and fresh selected executions remained needed for general improvement claims.
  • Broader synopsis gaps: Glue evaluation, retry-inclusive billing, explicit SLA probabilities and all proposed original regimes/baselines were not delivered by the B-lite experiment.
  • Formal delivery: repository drafts and a demo are not evidence that the department accepted a final report or revised synopsis.
The honest achievementWe built a reproducible bounded advisor and measured its behaviour. The next step was to investigate where small controlled evidence stops being enough—not to inflate a completion percentage.

Sources: full crosswalk · original advisor’s independent-validation plan.

13 · Why did the project direction change?

We needed a research question beyond “use an ML library.”

Training LightGBM and adding Dask do not by themselves create a new scientific method. The later direction asked a narrower question: can cheap input samples guide configuration choices when full jobs behave differently under memory pressure?

A probe is a small trial execution on sampled input. It can reveal actual behaviour before committing to a full execution. But if it takes longer than the saving it enables, it is a poor choice for that request.

Two traps we wanted to investigate

Fidelity trap

A quarter-size job is comfortable in RAM, while the full job crosses spill or restart thresholds. A stable small result can still misrepresent the full case.

Economics trap

A sample may run for only a few seconds, but so does the full job. Paying for several samples can cost more than simply using a reasonable setting.

Partition-aware means paying attention to how input is divided. Adaptive would mean deciding what to inspect or how to proceed based on available evidence. These were research aims; a validated online adaptive controller was not established.

Simple baselines matter. If a rule based on file sizes reaches the same good decision without a probe, the probe needs to show extra value. A more complicated technique does not win merely because it is more complicated.

Sources: research protocol · later plan and gates.

15 · What did 768 attempts teach us?

Memory scaling looked useful; the partition heuristic did not earn a win.

For each instance, a probe can select the setting it thinks is fastest. We then look at that setting’s full-engine time and compare it with the fastest complete full reference.

Selected full-engine regret = (chosen full time / best full time − 1) × 100 Toy example: best full time 10 s; probe chooses a setting taking 12 s. Regret = 20%. Lower is better.

Against the matched-memory uniform method, partition-tail was better on two instances, equal on three and worse on five. The ranking result therefore did not establish an advantage for partition-tail. Only two runtime repeats and one generation seed limited the evidence.

The 0.11% median regret is not 99.89% prediction accuracy. It measures selected-setting runtime relative to the best eligible full setting. It does not include profiling cost, prove reliability or measure generalization to unseen workloads. Replaying choices over all twelve instances also selected settings with three unsuccessful recorded full outcomes.

The cost changed the interpretation

The later screen review constructed an eight-probe-per-instance profile plus preparation costing a median 31.20 seconds, versus 3.80 seconds for a matched historical fixed full comparator. This is an historical cost construction, not a fresh online request. It showed why improving a ranking metric alone was insufficient.

What we achieved hereWe built a reproducible experiment system, found where small/full behaviour disagreed, and rejected an unsupported “partition-tail is better” claim. Negative evidence narrowed the next question instead of just encouraging more runs.

Sources: screen results · deeper screen review.

16 · Stage A: isolate mechanisms

Separate hot keys from uneven partitions.

Key skew means some key values occur much more often than others. Partition imbalance means input files/chunks have very different row counts. These can occur together, but they are not the same thing. Stage A varied them separately.

2 families × 4 patterns × 2 memory settings × 3 repeats = 48 full runs Patterns: balanced / key skew only / partition imbalance only / both

Stage A used two million fact rows, seed 911, eight fact files, two single-thread workers, and 1 GB or 2 GB per worker. For joins, the declared dimension relation was retained. One new generation seed with three runtime repeats is still a development diagnosis, not broad independent validation.

17 · Stage B: are quiet samples trustworthy?

All samples succeeded. That did not make them reliable warnings.

8 Stage A instances × 2 fractions × 2 target caps × 3 repeats = 96 probes Fractions: 1/8 = 12.5% of fact rows; 1/4 = 25% of fact rows

The 48 existing Stage A full outcomes were reused as historical references; they were not rerun. Stage B prepared 16 deterministic samples, one per instance/fraction, reused across caps and repeats. The samples at the two fractions were non-nested. For joins, the full right-hand dimension remained present while fact rows were sampled.

Why not give a quarter-size sample the full memory budget?

That may make the sample artificially comfortable. Stage B used a declared memory mapping with a fixed floor:

floor = 536,870,912 bytes (512 MiB) effective probe cap = round(floor + fraction × (target cap − floor))

See the actual mapped cap

Arithmetic from the frozen Stage B mapping, not a running probe.

25% sample at a 1 GB target → 652,653,184 bytes per worker.

The floor acknowledges that not every memory cost shrinks with fact-row count. It is a protocol choice, not a measured 512 MiB idle baseline. Observing roughly 75 MB initial worker RSS does not justify replacing that floor: graph state, joins and other allocations need not scale proportionally.

What happened?

96/96 probes succeeded and were “quiet”: no declared spill/pause/restart/nanny warning or quality flag. However, eight of 32 comparison groups paired quiet probes with historical full pressure. These are four instance/low-cap cases observed at two fractions, not eight independent unseen workloads.

A false-reassurance candidate is not simply a failed job.The full warning label includes spill/pause/restart evidence and failures. Some full jobs completed despite pressure. Therefore eight discrepancy groups do not establish a calibrated 25% false-negative rate or 75% classifier accuracy.

The six-probe selection replay chose 1 GB for every instance, mapping to 17/24 historical full successes. Fixed 2 GB and the file-metadata baseline mapped to 24/24. These outcomes came from the existing table, not newly executed policy decisions.

Sources: Stage B results · review and cost interpretation · mapping and protocol.

18 · Understanding RAM and spill

A 1 GB limit does not mean “nothing happens until 1 GB.”

The retained research settings include several action thresholds. They try to react before the worker exceeds its budget. Memory can also change between monitoring checks; the limit is not a hard operating-system sandbox wall.

Memory termMeaningWhy it matters
RSSResident set size: RAM pages currently attributed to the worker process.Includes more than Dask’s managed task-result data.
Managed memoryData tracked by Dask’s worker data store, with its size estimates.Some managed objects can be moved from RAM to disk.
Unmanaged memoryOther process memory, such as active task allocations, interpreter/native-library state or allocator effects.Not all of this can be relieved by spilling stored results.
SpillWrite some managed data to disk and retrieve it when needed.Can relieve RAM pressure, but adds I/O and does not make disk a free substitute for RAM.
PauseStop taking up more work under pressure.Running tasks may still have outstanding allocations.
Nanny restartA supervisor terminates/restarts a worker under its memory policy.It can interrupt/retry work. It is not proof of an OS OOM kill.

At a 1 GB cap, a worker can spill around the 700 MB process-pressure level even though it has not reached 1,000 MB. It can also begin managed-data spill near its managed target. If active work allocates memory rapidly, it can move past thresholds before the next monitor check finishes reacting.

The measurement record includes both peak stored spilled disk bytes and cumulative spill-write bytes. The first is the largest retained spill-store size observed; the second counts writes over time. They need not be equal. Temporary scratch storage is different again from durable datasets and diagnostic logs.

Why did runs consume disk space?Datasets and reusable sampled inputs are stored on disk, as are retained results and diagnostics. Temporary Dask spill is another category. “6 GB after many attempts” does not mean each raw JSON result occupies hundreds of megabytes. Repeats can reuse inputs; datasets, samples and logs have different lifetimes.

19 · Measuring memory is itself a research problem

A stored peak can be lower than a later termination reading.

The exporter recovered 321 worker lifetimes from 144 Stage A/B attempts: Stage A has 129 lifetimes (96 initial, 33 added), and Stage B has 192 initial lifetimes. A restarted process gets a new lifetime row. We do not merge all its readings into an imaginary never-restarted worker.

The collector samples every 50 ms and persists snapshots around every 250 ms. The recorded memory-monitor interval is 100 ms. These mechanisms are asynchronous. Abrupt termination can happen after the last saved sample, and a short peak can occur between checks.

33 / 37Terminated lifetimes whose retained sampled peaks were below the 95% threshold.
37 / 37Corresponding nanny-event RSS readings above that threshold.
36 / 37Events with an RSS reading higher than the saved worker peak.

A real exported example, lifetime A:b1c5da22aac9c6f6d07d814f:w02, retained a peak of 638,382,080 bytes, but its nanny event observed 999,092,224 bytes under a 1,000,000,000-byte cap. That is roughly 63.8% versus 99.9% of the cap. Both readings should remain attached to their sources.

Baseline RSS is the first plugin sample, not guaranteed clean idle memory. Largest observed RSS is still only an observation, not the true continuous-time maximum. The prototype therefore marks these memory representations exact_peak_known=false and automatic_regression_target=false.

Two arithmetic mistakes to avoidAdding every lifetime’s maximum does not give simultaneous cluster RAM, especially after restarts. Subtracting an independently timed managed-memory peak from an RSS peak does not reliably give unmanaged-memory usage.

The read-only export checked 1,507 diagnostic-file hashes, matched all 321 snapshots to telemetry and retained missing values as null/blank. Eight synthetic exporter tests passed. None of that required a new physical benchmark.

20 · Could one cheap probe rescue the idea?

It repeated metadata’s choices while adding cost.

The next idea reduced the six-probe workflow to one quarter-size, low-target-cap observation per decision. It used the maximum individual worker sampled peak divided by that worker’s effective cap. A post-hoc cutoff of 0.55 separated the current groups.

But the same four low-cap versus four high-cap choices could already be made using input metadata. A visible separation in the development table is not enough: the probe needs to change useful decisions beyond what a cheaper baseline already knows.

The stronger metadata rule

Metadata means facts available without executing the sampled workload: row counts, the largest fact-file row count, the number of payload columns and dimension rows. The prototype constructs dense-input memory scenarios from those descriptors.

N = fact rows; R = dimension rows; P = payload columns Nmax = largest fact-partition rows; W = 2 workers D = 8 × (P + 1) × N + 16 × R dense total input-byte scenario L = 8 × (P + 1) × Nmax largest fact-partition scenario Mlo = 128 MiB + D/W + L Mhi = 128 MiB + D/W + 3L

If the upper scenario is no more than 70% of a 1 GB cap, select 1 GB. Otherwise consider 2 GB under the same rule; abstain if neither scenario fits. These are hand-set development assumptions, not measured RSS or a guaranteed statistical memory bound.

Balanced toy metadata calculation

Two million fact rows, 16 payload columns, no dimension, eight equal files: D = 272 MB and L = 34 MB.

Upper scenario = 134.22 + 136 + 102 = 372.22 MB. It is below 700 MB, so the rule selects 1 GB.

Same rows, one large file

Largest fact file = 1.3 million rows. L = 176.8 MB; total D is still 272 MB.

Upper scenario = 134.22 + 136 + 530.4 = 800.62 MB. It exceeds 700 MB but fits 1,400 MB, so the rule selects 2 GB.

These are counterfactual replays: “What would this rule have selected using this one existing observation?” They are not newly executed requests. Each decision receives one probe observation; the three repeats are not averaged into that decision input or counted as independent new workloads.

What does “gate closed” mean?

The checked-in policy has admission_enabled=false. Even optimistic supplied cost estimates do not permit a probe. The pure decision module can select from metadata or abstain. The proposed 48-attempt pilot has enabled=false and no implemented execution runner.

The result is useful, even though it is negative.For these short one-shot jobs, we found no extra information benefit over metadata and no demonstrated profiling payback. We implemented explicit decision contracts and preserved evidence limits instead of claiming a validated improvement.

Sources: feasibility report · disabled policy and parameters · prototype contracts.

What should happen next?

  1. Form a specific revised hypothesis. Identify information that is unavailable cheaply from metadata but can change a useful decision.
  2. Choose the use case and objective before collecting more data. Short one-shot jobs currently do not repay profiling. A repeated-job use case is only a candidate scope change, not a result we already have.
  3. Compare strong simple baselines and closest prior work. Fixed settings and size-aware metadata must get a fair comparison. An ML library or Dask backend alone is not novelty.
  4. Predeclare a bounded protocol and untouched validation groups. Define all costs, failure handling, stop criteria and the final independent test.
  5. Only then revisit physical collection. Existing admission and the draft pilot stay disabled until the design is revised and reviewed.

A simple way to understand profiling payback

Toy repeated-job scenario only: One-time profiling costs 30 seconds. Each later job saves a genuine 3 seconds → 10 executions recover that time cost. Break-even reuse count = ceil(profile cost / positive per-run saving) If saving ≤ 0, there is no finite break-even.

This arithmetic does not establish an amortized SAFE-Pipe result. Real reuse, drift, fair cluster reuse for baselines and resource costs would need their own protocol. It is one possible question to investigate, not the current project claim.

26 · Glossary and spoken explanations

Short answers you can explain in your own words.

What is the motivation of SAFE-Pipe?

Different worker, thread and memory settings can make the same data job faster, slower or more resource-heavy. We want a transparent way to compare a bounded set of settings before execution, respecting a deadline and the limits of our evidence.

What is the difference between a baseline and our method?

A baseline is a simpler comparison we must beat or learn from: a fixed setting, family-median runtime estimate or metadata rule. Our original advisor uses a fitted predictor; our research explored additional probing. A baseline can be the strongest practical result, as metadata currently is in the one-probe comparison.

What is a workload family versus a workload instance?

A family is an operation category, such as groupby. An instance is a particular input with a size, seed, layout and skew pattern. Many runtime repeats of one instance do not become many independent workload families.

What are skew and partition imbalance?

Skew can mean uneven frequencies of keys, such as one customer ID appearing very often. Partition imbalance means uneven file/chunk sizes. They affect computation differently and must be distinguished. Stage A varied the two factors separately.

What is a straggler?

A task or worker that takes much longer than the others and delays overall completion. One unusually large partition or expensive key group can create such a bottleneck. Input layout alone does not prove the exact cause of every straggler.

What is a probe and what is fidelity?

A probe is a small trial execution. Fidelity asks whether it preserves the behaviour relevant to the full job. A sample can return the correct small-data result but still misrepresent full-job memory pressure or configuration ranking.

Why does a repeat not count as a new workload?

A repeat reruns the same experimental condition to observe timing/outcome variation. It helps assess noise. It does not independently change data size, seed or family, so counting repeats as independent workloads exaggerates evidence diversity.

What are regression, residual and overfitting?

Regression predicts a number. A residual is a difference between an observed outcome and its prediction, defined in our calibration on the log scale. Overfitting means learning quirks of the training evidence that do not carry over. Small trees, regularization and a grouped test help, but do not prove broad generalization.

What are OOD and abstention?

OOD means out of distribution: input differs from what the evidence supports. Abstention means the system declines to recommend when support or constraints are inadequate. The older gate used family/size heuristics; the explained advisor requires exact frozen descriptors. Neither makes arbitrary unseen jobs validated.

Does failure-aware mean we trained a failure classifier?

No. The original study had no failures, so it used deterministic guards. Later research recorded failures and worker events, but those concentrated development observations still do not establish a general calibrated failure model. Worker terminations are not interchangeable with independent failed-job examples.

What do “success,” “quiet” and “safe” mean?

Success means the recorded attempt completed successfully. Quiet means no declared warning signal and acceptable recorded quality under the research rule. “Safe” is a stronger claim we have not generally established. A successful full run can contain spill or worker restarts.

What are replay and counterfactual?

A replay applies a decision rule to existing measurements. A counterfactual asks what a different rule would have selected from that evidence. Neither automatically measures a new online request, a fresh selected job or independent real-world performance.

What is an oracle?

An analysis-only comparator allowed to know outcomes after the fact. It can estimate optimistic headroom, but that knowledge cannot be supplied to a real pre-run decision. If even optimistic possible savings cannot repay profiling, that is a useful feasibility warning.

What does independent validation require?

Freeze the method, objective, supported domain and baselines before evaluating on untouched workload groups. Charge the complete decision/request costs and actually execute the selected full work when making online-performance claims. Do not tune on the final test and still call it untouched.

What is novelty, and why is it still open?

Novelty requires a meaningful contribution relative to prior work, not merely a new codebase. Profiling, memory-based tuning and multi-fidelity search already have related research. Our current infrastructure and negative findings are useful, but a validated new selection method and a publishable contribution remain unestablished.

What is the difference between a measured result and an example?

A measured result comes from a named saved experiment/report. A toy example explains an idea using invented numbers. This guide labels toy arithmetic and conceptual figures; do not quote their values as experimental measurements.

Why can 100% observed coverage or 24/24 success be misleading?

Each describes a particular small evaluation table under a defined rule. Coverage concerns an upper prediction exceeding observed runtime; success concerns job completion. Neither is automatically a universal success probability or proof of performance on new workloads.

What does a passing hash audit prove?

It proves the checked files match their saved expected identities under the audit. It helps preserve provenance and detect accidental changes. It does not certify the chosen statistical design, novelty, causal interpretation or future reliability.

What is the simplest honest one-minute project explanation?

“We built a local Dask configuration advisor and measured four profiles across eight settings with three repeats. LightGBM’s test median percentage error was 13.84%, with limited workload diversity. We then investigated whether samples could guide memory-sensitive full jobs. The screen, Stage A and Stage B exposed sample/full mismatches and limits in saved memory peaks. A one-probe rule did not improve decisions over metadata after paying its cost. The guarded implementation passed Windows tests, but admission stays disabled while we redesign the research hypothesis.”
